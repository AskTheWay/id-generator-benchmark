分库分表 × ID 生成

分库分表是分布式 ID 的"第一推动力"—— 数据打散后, 数据库自增只在分片内成立。 下面用 4 个 schema 模拟 4 个分片, 四个经典场景各自独立运行、可反复重放(总量 < 2 万行, 仅演示分布效果)。

① 独立自增 → 跨分片撞号 反面教材

各分片 AUTO INCREMENT 都从 1 开始: 单分片内唯一, 跨分片大面积撞号——这就是"为什么不能继续用数据库自增"的最直接证明。

② 步长自增 → 零协调全局唯一

分片 i 用 START=i+1, INCREMENT=N: ID 交错而不相交。代价是扩容(如 4→8 分片)要迁移一半数据, 且跨分片无序。教学玩法: 先 4 片跑一次, 改 8 片再跑, 观察号段区间变化与扩容困境。

③ 基因法 → 凭 ID 直路由

订单 ID 低位嵌入用户基因(user_id % 64), Snowflake 作基底: order_id = (snowflake << 6) | gene。仅凭 ID 提取低 6 位即可定位分片, 同一用户的订单 100% 同片, 查询免广播。基因位数限制了分片数上限(6bit → 2/4/8/16/32/64)。

④ range 分片 + 单调 ID → 写热点

按月 range 分片, 最新分片承载绝大部分写入(热点); 对比 hash 分片的均匀——但范围查询要广播。这正是 TiDB auto_random 打散自增主键防热点的原因: "有序"在分布式存储里会从优点变成缺点。

离线摆渡(气隙网络)模拟

打印设备在监狱等无法联网环境, 数据定期经光盘/U 盘"摆渡"回中心(sneakernet)。 三层防线: 站点号入 ID(空间防撞) + 本地持久水位(时间防重, 免疫时钟问题) + 中心预分配配额(重装防丢); 摆渡导入时唯一索引做最终兜底。 站点状态存本地 JSON 文件(模拟终端本地盘), 只有摆渡导入才接触数据库。

反面教材: "裸奔终端"互相撞号 事后检测太晚

两台终端都没嵌站点号、各自从 1 发号 → 摆渡导入时被中心唯一索引拦下。 摆渡周期是天/周级, 发现撞号时标签早已打印流通, 只能作废重打——唯一性必须在"事前"保证。

方法论:压测前预热连接池, 排除冷启动建连对首请求延迟的污染;压测采用线程池并发调用, 每次调用单独计时;延迟分位数(P50/P90/P99)按线性插值计算。注意:Python GIL 下压测客户端自身可能是瓶颈, 本地生成方案的数据代表下界。
